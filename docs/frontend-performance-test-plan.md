# 프론트엔드 성능 테스트계획서

작성일: 2026-10-26 · 대상: LIVE:GUARD 시청자·스트리머·시스템 운영자 화면

## 1. 범위와 실행 원칙

**평가 대상은 프론트엔드다.** 생산 빌드와 실제 Chromium을 실행하고, 시험용 HTTP/SSE 서버가 재현 가능한 메시지·상태·검토 요청을 보낸다. 실제 EventSource, API 클라이언트, Vue 화면, 승인 요청, 재연결 처리를 통과한다. AI 호출·정확도·비용, 실제 백엔드 처리량, DB 저장 성능은 평가하지 않는다.

시험용 서버를 사용하는 목적은 서버·모델 지연을 고정하고 FE 처리 비용을 확인하기 위해서다. 결과의 `100건/초`는 한 브라우저에 들어오는 이벤트 부하이며 실제 사용자 100명의 접속 용량을 뜻하지 않는다. 통과 여부는 이 문서의 FE 시험 조건에 한정한다. 실패한 목표는 **미달**로 기록한다.

## 2. 핵심 프론트엔드 성능 지표

| 측정 항목 | 측정 내용 | 초기 목표 | 측정 방법·관련 TC |
| --- | --- | --- | --- |
| 채팅 표시 지연 | 메시지 이벤트 수신 후 해당 메시지가 화면에 반영될 때까지 | P95 100ms 이하 | 수신→DOM 변경과 수신→다음 rAF 콜백을 각각 계측. TC-01/02 |
| 실시간 이벤트 반영 지연 | SSE 상태 이벤트 수신 후 채팅 표시 상태 변경까지 | P95 100ms 이하 | 고정 상태 이벤트 200건의 DOM/다음 프레임 지연, 비공개 원문 제거. TC-03 |
| 채팅 처리량 | 초당 들어오는 메시지를 누락 없이 화면의 최신 창에 반영하는가 | 100건/초 × 5분 | 시험 서버가 30,000개 ID 발송, 브라우저 수신·관찰 수와 최신 80/200개 대조. TC-02 |
| 프레임 속도(FPS) | 채팅 갱신 중 화면의 프레임이 유지되는가 | 60FPS 지향 | 프레임 간격 P95 및 50ms 이상 장기 작업. 60Hz의 16.7ms는 참고값. TC-01/02/05 |
| 사용자 입력 응답성(INP) | 클릭·키 입력이 다음 화면 갱신에 반영되는 속도 | 200ms 이하 | Event Timing 상호작용 지연과 승인 클릭→버튼 비활성 다음 프레임을 기록. TC-04/07 |
| 메모리 안정성 | 방송이 길어져도 JS heap·DOM이 계속 늘지 않는가 | 1시간 후 안정화 확인 | 실제 60분 실행, GC 후 0/15/30/45/60분 heap·DOM·이벤트 리스너. TC-05 |
| 메시지 정합성 | 누락·중복·순서 오류가 있는가 | 누락·중복·순서 오류 0건 | 발송 ID와 관찰 수, 시청자 최신 80개/운영자 최신 200개, 재연결 뒤 대조. TC-01/02/06 |
| 화면 초기 로딩(LCP) | 첫 탐색의 주요 콘텐츠가 표시되는 시간 | 2.5초 이하 | 역할 3종 × 화면 2종 × 냉시작/재방문 × 3회, 브라우저 LCP 관찰. TC-07 |

100ms·100건/초·메모리 한계는 프로젝트 시험 기준이다. LCP 2.5초·INP 200ms는 일반 웹 성능 권장 기준을 참고한다. 이번 결과는 실험실 표본이며 실제 서비스 이용자들의 현장 P75 판정으로 표현하지 않는다. 부가 지표 CLS는 0.1 이하를 사용한다.

`MutationObserver`는 DOM 시각이다. DOM 변경 뒤 첫 `requestAnimationFrame` 콜백은 브라우저의 프레임 반영 기회에 대한 대용 측정이며 **실제 픽셀이 모니터에 표시된 시각을 직접 측정한 값은 아니다**. 두 값을 원자료에 모두 남긴다. Event Timing은 16ms 미만 이벤트를 생략할 수 있어 관찰값이 없을 때는 0ms 대신 16ms 이하 상한으로 기록한다. 소수의 통제된 상호작용 결과를 전체 사용자의 INP 달성으로 일반화하지 않는다.

## 3. TC별 성능 검증 목적과 합격 기준

| TC | 확인하려는 성능의 목적 | 시험 조건 | 확인 지표·판정 |
| --- | --- | --- | --- |
| TC-01 정상 채팅 | 평소 채팅 속도에서도 표시가 뒤처지거나 메시지가 사라지는지 확인 | 10건/초 × 실제 5분, 3,000건; 운영자·시청자 동시 열기 | 발송 3,000건 모두 관찰, 최신 창 정확·중복 0, 수신→다음 프레임 P95 ≤100ms |
| TC-02 채팅 폭주 | 짧은 시간에 채팅이 몰릴 때 렌더링 병목·프레임 저하·정합성 손실을 찾기 | 100건/초 × 실제 5분, 30,000건 | 발송 30,000건 모두 관찰, 최신 창 정확·중복 0, 수신→다음 프레임 P95 ≤100ms. 프레임/메인 스레드 점유도 기록 |
| TC-03 상태 이벤트 반영 | 공개 채팅의 숨김·검토 상태가 화면에 늦게 남는지, 다른 시청자에게 원문이 노출되는지 확인 | 고정 1,000건 중 최근 200건을 SSE로 PUBLIC→HELD 변경 | 운영자 200행 상태 일치, 비인가 시청자 원문 0, 수신→다음 프레임 P95 ≤100ms. 상태 판단 내용 자체는 평가하지 않음 |
| TC-04 승인 인터랙션 | 운영자가 연속 처리할 때 즉시 피드백을 받고 중복 승인 요청을 보내지 않는지 확인 | 고정 강퇴 요청 50건, 승인·기각 교대, 응답 120ms 고정 | 클릭→비활성 다음 프레임 P95 ≤200ms, 요청당 전송 1회. 실제 강퇴 실행은 시험하지 않음 |
| TC-05 장시간 안정성 | 방송 후반에 메모리·DOM 증가로 관제가 느려지거나 중단되는지 확인 | 실제 60분. 처음 5분 10건/s, 다음 5분 100건/s, 이후 10건/s; TC-01/02 포함 | 15분 예열 이후 화면별 GC 후 heap 증가 ≤5MiB, 최신 DOM 200/80행 유지, 브라우저 예외 0. 최종 30/45/60분 추이도 함께 공개 |
| TC-06 SSE 연결 복구 | 네트워크가 끊긴 동안 놓친 최신 채팅을 복구하고 중복 표시하지 않는지 확인 | SSE 10초 단절 중 메시지 계속 적재, 복구 3회 | 서비스 복원 후 10초 이내 최신 창 일치, 중복·순서 오류 0. 실제 인터넷 장애 전체를 모사하는 시험은 아님 |
| TC-07 초기 로딩·입력 | 첫 진입이 느리거나 버튼·키보드 조작이 지연되는지, 작은 화면이 깨지는지 확인 | 3개 역할 × 1440×900/390×844 × 냉시작/재방문 × 3회 = 36회 | 각 탐색 LCP ≤2.5초, Event Timing 상호작용 상한 ≤200ms, CLS ≤0.1, 가로 넘침 0. 실험실 결과로 판정 |

TC-01/02는 TC-05의 첫 10분을 겸한다. 동일한 두 브라우저 화면을 60분 유지하며 시험 중 가상 시계로 시간을 앞당기지 않는다. 승인·복구·로딩 시험은 장시간 시험 시작 전에 완료한다. 장시간 실행 중 다른 무거운 시험은 병행하지 않는다.

## 4. 재현과 증거

- 기존 10초 합성 기준선 재측정: `PERF_OUTPUT=<별도 JSON 경로> node scripts/performance-smoke.cjs`, 3회. 과거 원자료는 보존한다.
- FE 전용 전체 시험: `node scripts/frontend-performance-suite.cjs`. 생산 API 모드 빌드를 임시 폴더에 만들고 격리 서버를 실행한다. 원자료: `docs/evidence/performance/recheck-2026-10-26/frontend-suite.json`.
- 계측 확인용 단축 실행: `node scripts/frontend-performance-suite.cjs --quick`. 이 결과는 정식 TC의 5분·60분 통과 자료로 사용하지 않는다.
- 실행 환경, 커밋과 미커밋 파일 목록, 실제 시간, 브라우저 버전, TC별 원자료, heap 간격 표본, 브라우저 예외를 함께 저장한다.
- [결과서](frontend-performance-test-results.md)에 각 TC의 실행 결과를 기록한다. 장시간 시험 중에는 진행 상태를 표시하고, 완료 후 실제 기준에 따라 통과·미달을 확정한다.
