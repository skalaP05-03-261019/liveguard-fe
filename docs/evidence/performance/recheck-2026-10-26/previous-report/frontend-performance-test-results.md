# 프론트엔드 성능 테스트결과서

작성일: 2026-10-26 · 기준: [테스트계획서](frontend-performance-test-plan.md) · 원자료: [frontend-smoke.json](evidence/performance/frontend-smoke.json)

## 1. 이번 실행 범위

macOS 14.0, Node 24.20.0, Chromium 156.0.8078.4, 1440×900, 생산 빌드 미리보기, 목업 스트리머 화면에서 **1회 탐색 측정**했다. FE HEAD는 `c75e0bf`이며 작업 트리의 미커밋 UI 변경이 빌드에 포함됐다. `scripts/performance-smoke.cjs`가 반응형 목업 배열에 공개 채팅을 넣었다. 실제 시청자 다중 접속, SSE, Backend, DB, Agent 및 네트워크 부하는 발생시키지 않았다.

`MutationObserver`로 메시지 DOM 추가 시각을 측정했다. 아래 지연은 **데이터 주입→DOM 추가**이며, 화면 페인트·SSE 수신→페인트 지연은 아니다. 프레임 간격은 `requestAnimationFrame`, heap은 GC 후 Chrome CDP 값이다. 표본 1회이므로 환경 간 성능 비교와 공식 Web Vitals 판정에 사용하지 않는다.

## 2. 측정 결과

| 조건 | 실제 주입률 | 주입/DOM 관찰 | DOM 추가 지연 P50 / P95 / 최대 | 프레임 간격 P95 / 최대 | 50ms 장기 작업 | GC 후 heap 시작→끝 |

| 100건/초 × 10초 | 99.93건/초 | 1,000 / 1,000, 미관찰 0 | 2.4 / 2.8 / 4.7ms | 16.7 / 16.8ms | 0건 | 4.33→5.32MiB |

두 번째 구간 직후 스트리머의 DOM 채팅 행은 최근 **200개**였다. 최신 200개 메시지를 한 번에 `HELD`로 바꾸는 합성 시험에서는 다음 프레임에 200개 행 모두 새 상태였고 코드 실행→다음 프레임까지 4.1ms였다. 브라우저 예외는 0건이었다. 이 값은 API 판정 반영이나 다른 시청자의 비공개 차단을 증명하지 않는다.

이번 측정의 100건/초 P95가 10건/초보다 낮은 이유는 이 한 차례의 Vue 갱신·타이머 배치와 측정 위치에 따른 현상일 수 있다. 빠른 조건이 본질적으로 더 효율적이라는 결론은 내리지 않는다. DOM 추가 지연은 페인트보다 앞서 기록되고, 합성 메시지에는 실제 채팅 판정·네트워크 비용이 없다.

기능 회귀 시험은 관련 SSE 배치·이벤트 버전·승인 동작 **5개 항목이 통과**했다(`node --test --test-name-pattern='chat bursts|versioned SSE|new decision requests highlight|API operator on a stale review|API kick rejection' tests/live-chat.test.cjs`). 이 통과 여부는 위 성능 목표의 통과로 계산하지 않는다.

## 4. 해석과 다음 측정

합성 시험은 이 환경의 짧은 구간에서 스트리머 채팅 DOM이 초당 100개 주입을 따라간다는 **초기 근거**다. 제안서의 핵심 KPI인 `SSE 수신→페인트 P95 ≤100ms`, `실제 100건/초 × 5분`, `60분 누수 없음`은 아직 검증되지 않았다.

다음 실행에서는 별도 로컬 방송에서 서버 저장 ID와 SSE ID를 기록하고, 브라우저의 이벤트 수신·재조회 완료·다음 페인트 시각을 분리해 측정한다. 시청자 80개·스트리머 200개 창과 60분 heap 추이를 함께 검증한다. 공식 기준인 LCP·INP·CLS는 역할별 페이지를 모바일·데스크톱에서 반복 측정한다.
