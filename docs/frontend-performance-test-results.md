## 1. Phase 1 대비 확인된 성능 개선

**성능 개선의 핵심은 이벤트가 몰릴 때 불필요한 API 호출을 줄이고, 화면에 그리는 채팅 개수를 제한해 브라우저의 렌더링 부담을 낮춘 것이다.** Phase 1 태그와 60분 시험에 사용한 현재 생산 빌드를 같은 노트북·Chromium·시험 서버에서 각각 3회 실행했으며, 세 번 모두 같은 결과였다.

| 개선 항목 | Phase 1 | 현재 측정 빌드 | 개선율 | 변경 이유·방식 |
| --- | ---: | ---: | ---: | --- |
| 채팅 이벤트의 전체 API 호출 | 500 | 2 | **99.6% 감소** | 이벤트를 묶고 필요한 데이터만 조회해 중복 요청과 응답 처리 부담을 줄임 |
| 진행 이벤트의 추가 API 호출 | 500 | 0 | **100% 감소** | 진행 이벤트의 목록 재조회를 생략해 불필요한 요청·응답 처리를 없앰 |
| 운영자 채팅 렌더링 개수 | 1,000 | 200 | **80% 감소** | 최근 200건만 화면에 그려 브라우저의 렌더링 부담을 낮춤 |
| 시청자 채팅 렌더링 개수 | 1,000 | 80 | **92% 감소** | 최근 80건만 화면에 그려 브라우저의 렌더링 부담을 낮춤 |

채팅·진행 이벤트 시험은 각각 100개의 SSE 이벤트를 한 번에 보냈다. DOM 시험은 서버가 동일한 공개 메시지 1,000개를 반환했다. 이벤트에 따른 호출을 분리하기 위해 5초 주기 세션 폴링은 두 버전에서 동일하게 껐다. 추가 API 호출 수는 초기 조회가 끝난 뒤부터 집계했다.

Phase 1은 채팅 이벤트마다 인증·메시지·문맥 검토·강퇴 검토·사건을 다시 조회했다. 현재는 채팅 이벤트 100개를 하나의 갱신으로 묶어 인증 1회·메시지 1회만 조회한다. 사건·검토의 불필요한 조회는 300회에서 0회로 감소했다.

비교 기준: `phase1` = `a681476d1d9bf2ad4f60ff531b716e650a84cbdf`. 현재는 아래 60분 측정과 같은 보관 빌드(`production-build.zip`)를 사용했다. 비교 원자료는 `phase1-comparison.json`이다.

**개선율의 의미:** 위 비율은 요청 수·채팅 DOM 행 수의 감소율이다. LCP·렌더링 지연·전체 메모리가 같은 비율로 빨라졌다는 뜻은 아니다. 80ms 묶음 처리는 요청을 줄이는 대신 표시까지 대기 시간을 추가하며, 현재 100ms 지연 목표 미달은 아래에 그대로 기록했다.

## 4. 환경과 재현 범위

- 실행 호스트: Apple M2 · 8GiB RAM · darwin 23.0.0 · Node v24.20.0 · Chromium 156.0.8078.4.
- 60분 시험 FE 커밋: `c75e0bfba4594866948109a90a5b959c4f433acd` + 당시 미커밋 작업 트리. API 호출 수·DOM 행 수는 1절에서 Phase 1과 직접 비교했다. LCP·INP·60분 heap의 Phase 1 기준선은 없어 해당 지표의 속도·메모리 개선율은 산출하지 않았다.
- 생산 API 모드 빌드, 실제 HTTP/EventSource, 고정 시험 응답. 시청자·운영자 화면을 동시에 열었다. 시험용 서버 지연과 브라우저 실행 조건이 포함되며 실제 운영 네트워크·동시 접속자 용량을 뜻하지 않는다.
- 390px 시험은 같은 노트북에서 브라우저 폭을 줄인 반응형 시험이다. 냉시작은 새 브라우저 컨텍스트의 첫 탐색이며 OS 재부팅·실물 휴대폰 측정을 뜻하지 않는다. 채팅은 고정된 짧은 일반 텍스트를 사용했다.
- TC-01/02는 TC-05의 첫 10분이다. 이후 같은 두 화면에서 채팅을 계속 흘려 실제 60분을 채웠다. 가상 시계로 시간을 앞당기지 않았다.
- 승인 응답을 120ms로 고정해 클릭→진행 표시만 평가했다. 실제 제재의 성공·속도는 평가하지 않았다.
- 시스템 운영자의 로딩 값은 현재 제공되는 API 빈 상태 화면 기준이다. 실제 다중 방송 집계 데이터를 채운 화면의 용량 검증은 포함하지 않는다.
- 브라우저 실행 예외: 0건.
